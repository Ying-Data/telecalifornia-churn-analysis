TeleCalifornia Churn Analysis

Methodology and How to Explore

A one-page reference to how this analysis was built, the choices behind it, and how to reproduce or explore it in five minutes.

What this project answers

TeleCalifornia, a California telecom serving 7,043 customers, loses its highest-paying customers to churn. This project quantifies the loss, predicts who will leave next, and prices a retention response. Four questions drive it: what is the exact churn rate and revenue impact, which segments are most at risk and why, can churn be predicted before it happens, and which retention actions pay back fastest.

Data and cleaning

Three Maven Analytics files are merged: customer records, ZIP-code population, and a data dictionary. The cleaning is intentionally conservative, with each null treated by business logic rather than blanket imputation.

DecisionTreatmentWhy
Service fields blank for no-internet customersFilled as "No Internet Service"The blank is a real category, not a missing value
120 negative monthly chargesClipped to 0, flagged separatelyBilling credits, not service revenue
ZIP-to-population join100% match on 7,043 recordsNo rows dropped for geography
Customers with status "Joined"Excluded from the modelThey have not yet had a chance to churn

Feature engineering

Sixteen columns are engineered from the raw data, including a contract-risk score, tenure and age segments, a service-bundle score, an estimated customer lifetime value, and a binary churn target. The full, commented logic lives in churn_analysis.py.

Model

A Random Forest classifier (200 trees, balanced class weights) predicts individual churn probability. It is evaluated on a stratified 80/20 split and a 5-fold cross-validation.

  • AUC-ROC: 0.9251 (5-fold CV: 0.9281 +/- 0.005)
  • Accuracy 85.1%, precision 73%, recall 76% on the churn class
  • Top drivers: contract risk, contract type, tenure, referrals
Feature integrity: a few monetary fields (Total Revenue, estimated CLTV) are correlated with tenure and therefore partly endogenous to the outcome, so the headline AUC is read conservatively. A production model would exclude any field generated after the churn decision and be validated on a forward time split rather than a random one.

Reproduce it

git clone https://github.com/Ying-Data/telecalifornia-churn-analysis.git
cd telecalifornia-churn-analysis
pip install -r requirements.txt
# place the raw Kaggle CSVs in data/, then:
python churn_analysis.py

The script prints the full findings to the console and writes data/telecom_clean_powerbi.csv (57 columns) for the dashboard.

Explore the dashboard

  1. Download output/TeleCalifornia_Churn_Dashboard.pbix.
  2. Open it in the free Power BI Desktop.
  3. Under Transform Data, point the source to your local copy of the CSV.
